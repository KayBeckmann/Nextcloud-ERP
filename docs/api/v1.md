# API v1

Basis: Nextcloud OCS-API-Konventionen. Alle Endpunkte liegen unter

```text
/ocs/v2.php/apps/erp/api/v1/...
```

## Auth

Nextcloud-Session-Auth (Cookie, Web-UI) oder HTTP Basic Auth mit
Benutzername/Passwort bzw. App-Passwort (z. B. für `curl`/CI). Jeder Request
braucht den Header `OCS-APIRequest: true` (OCS-Konvention, verhindert
versehentliche Browser-Same-Origin-Requests ohne CSRF-Schutz). Antwortformat
über `Accept: application/json` erzwingen — ohne diesen Header liefert
Nextcloud standardmäßig XML.

## Antwortformat

Standard-OCS-Hülle:

```json
{
  "ocs": {
    "meta": { "status": "ok", "statuscode": 200, "message": "OK" },
    "data": { "...": "..." }
  }
}
```

Bei Fehlern liefert Nextcloud denselben Umschlag mit `status: "failure"` und
passendem HTTP-Statuscode (siehe unten) — kein eigenes Fehlerformat nötig,
das ist bewusst Nextclouds eingebauter Mechanismus (`OCSBadRequestException`,
etc.), siehe [Roadmap Phase 2](../roadmap.md#phase-2--identität-rechte-und-api-grundlage).

## Rechteprüfung

Alle Endpunkte außer `/permissions/me` erfordern einen
**Nextcloud-Instanz-Admin** (Nextcloud-Standardverhalten: Controller-Methoden
verlangen implizit Admin, sofern nicht explizit mit `#[NoAdminRequired]`
geöffnet). Nicht-Admins erhalten `HTTP 403`. Details/Begründung:
[ADR-0008](../adr/0008-rechte-modell.md).

Die ERP-eigene Rechte-Matrix (`erp_permissions`) steuert **fachliche**
Modul-Berechtigungen für spätere Endpunkte (Projekte, Angebote, …), nicht den
Zugriff auf die Rechteverwaltung selbst.

## `GET /api/v1/status`

Öffentlicher Statuscheck (jeder eingeloggte User).

**Response `200`:**

```json
{ "app": "erp", "apiVersion": "v1", "appVersion": "0.1.0", "status": "ok" }
```

---

## `GET /api/v1/permissions/principals`

**Admin.** Liste aller Nextcloud-User und -Gruppen als wählbare Principals für
die Rechte-Matrix.

**Response `200`:**

```json
[
  { "type": "group", "id": "admin", "displayName": "admin" },
  { "type": "user", "id": "kay", "displayName": "kay" }
]
```

## `GET /api/v1/permissions/matrix`

**Admin.** Vollständige Rechte-Matrix.

**Response `200`:**

```json
{
  "resourceTypes": ["dashboard", "projekte", "..."],
  "permissionLevels": ["none", "read", "write", "approve", "admin"],
  "entries": [
    { "principalType": "group", "principalId": "monteure", "resourceType": "projekte", "permission": "write" }
  ]
}
```

## `PUT /api/v1/permissions/matrix`

**Admin.** Setzt (oder löscht, bei `permission: "none"`) einen einzelnen
Rechte-Eintrag.

**Body:**

```json
{
  "principalType": "user",
  "principalId": "kay",
  "resourceType": "rechnungen",
  "permission": "approve"
}
```

**Response `200`:** der gespeicherte Eintrag. **`400`** bei unbekanntem
`resourceType`/`permission` oder ungültigem `principalType`.

## `GET /api/v1/permissions/me`

**Jeder eingeloggte User.** Effektive Berechtigungen des aktuellen Users über
alle Ressourcen (User-Einträge + alle Gruppen, höchste Stufe gewinnt;
Nextcloud-Admins immer `admin`, siehe ADR-0008).

**Response `200`:**

```json
{
  "userId": "kay",
  "permissions": {
    "dashboard": "admin",
    "projekte": "admin",
    "...": "..."
  }
}
```

## `GET /api/v1/contacts/search?q=...`

**Jeder eingeloggte User.** Sucht in Nextcloud Contacts (`OCP\Contacts\IManager::search()`).

**Response `200`:**

```json
[{ "uid": "6b4bc26c-...", "displayName": "Leon Green", "emails": ["leon@example.com"] }]
```

## `GET /api/v1/contacts/links/{role}`

`role` = `customer` oder `supplier`. **Erfordert mindestens `read` auf
`ResourceType::Kunden` bzw. `::Lieferanten`** (ERP-Rechte-Matrix aus Phase 2).

**Response `200`:** Links inkl. live nachgeschlagenem `displayName`.

## `POST /api/v1/contacts/links`

**Erfordert mindestens `write`** auf die passende Ressource.

**Body:** `{ "contactUid", "role", "referenceNumber"?, "paymentTermsDays"?, "notes"? }`

**`400`** wenn der Contact in dieser Rolle bereits verknüpft ist oder `role`
ungültig ist.

## `PUT /api/v1/contacts/links/{id}` · `DELETE /api/v1/contacts/links/{id}`

**Erfordert `write`** auf die Ressource, die zur *bestehenden* Rolle des Links
gehört (wird serverseitig nachgeschlagen, nicht vom Client vorgegeben).
**`404`** wenn der Link nicht existiert.

---

## `GET /api/v1/calendar/calendars`

**Jeder eingeloggte User.** Kalender des aktuellen Users
(`IManager::getCalendarsForPrincipal()`), inkl. `writable`-Flag.

## `POST /api/v1/calendar/events`

**Erfordert mindestens `write`** auf den übergebenen `resourceType` (muss ein
bekannter `ResourceType`-Wert sein). Legt einen echten Kalendertermin an
(`ICalendarEventBuilder`/`ICreateFromString`, siehe ADR-0009) und verknüpft
ihn generisch mit `resourceType`+`resourceId`.

**Body:** `{ "calendarUri", "resourceType", "resourceId", "summary", "start", "end", "description"? }`
(`start`/`end` als ISO-8601-Datetime-Strings)

**`400`** bei unbekanntem `resourceType`/Kalender oder ungültigem Datum.

## `GET /api/v1/calendar/links?resourceType=...&resourceId=...`

**Erfordert mindestens `read`** auf den `resourceType`.

---

## `GET /api/v1/files/erp-folder`

**Jeder eingeloggte User.** Stellt die ERP-Ordnerstruktur im Home-Verzeichnis
des Users sicher (idempotent) und gibt sie zurück.

**Response `200`:**

```json
[{ "name": "ERP", "path": "/kay/files/ERP", "fileId": 331 }, "..."]
```

---

---

## `GET /api/v1/projects?status=...`

**Erfordert mindestens `read`** auf `ResourceType::Projekte`. `status` optional
(einer von `draft`/`quote`/`in_progress`/`waiting`/`done`/`archived`).

## `POST /api/v1/projects`

**Erfordert mindestens `write`.** Legt automatisch den Projektordner
`ERP/Projekte/<Nummer>` an (ADR-0010).

**Body:** `{ "title", "customerContactUid"?, "responsibleUserId"?, "notes"? }`

## `GET /api/v1/projects/{id}` · `PUT /api/v1/projects/{id}`

Lesen erfordert `read`, Schreiben `write`. `PUT` ersetzt alle veränderbaren
Felder vollständig (kein Patch) — `title`, `status` sind Pflicht.

---

## `GET /api/v1/projects/{projectId}/tasks` · `POST .../tasks` · `PUT .../tasks/{id}` · `DELETE .../tasks/{id}`

Einfache Projekt-Checkliste. Rechte-Gate wie bei Projekten selbst
(`ResourceType::Projekte`, ADR-0010 — Aufgaben sind Unterressource, kein
eigener Rechtebereich).

## `GET /api/v1/projects/{projectId}/orders` · `POST .../orders` · `PUT .../orders/{id}`

Einfache Auftragserfassung pro Projekt. **Eigener Rechtebereich**
`ResourceType::Auftraege`.

---

## `GET /api/v1/contacts/resolve?uid=...`

**Jeder eingeloggte User.** Löst eine Contact-UID zu einem Anzeigenamen auf —
für Projekte, deren Kunde nicht zwingend als `erp_contact_links`-Eintrag
existiert.

---

---

## `GET`/`POST /api/v1/vat-rates` · `PUT /api/v1/vat-rates/{id}`

**Erfordert `read`/`write` auf `ResourceType::Einstellungen`.** MwSt.-Sätze —
systemweite Stammdaten, kein eigener Rechtebereich (ADR-0011). Setzen von
`isDefault: true` entfernt automatisch den Standard-Status vom vorherigen
Satz (immer nur ein Standardsatz).

## `GET`/`POST /api/v1/work-types` · `PUT /api/v1/work-types/{id}`

**Erfordert `read`/`write` auf `ResourceType::Einstellungen`.** Arbeitsarten
(Monteur, Meister, …) mit Stundensatz und optionalem MwSt.-Satz-Bezug.

---

## `GET`/`POST /api/v1/articles` · `GET`/`PUT /api/v1/articles/{id}`

**Erfordert `read`/`write` auf `ResourceType::Artikel`.** Artikelstamm.
`GET /articles/{id}` liefert den Artikel inklusive aller Lieferantenpreise.

## `POST /api/v1/articles/{articleId}/supplier-prices` · `DELETE .../supplier-prices/{priceId}`

Lieferantenpreise pro Artikel (mehrere pro Artikel möglich, ADR-0011).

---

## `GET`/`POST /api/v1/products` · `GET`/`PUT /api/v1/products/{id}`

**Erfordert `read`/`write` auf `ResourceType::Produkte`.** Produkte/Bundles.
`GET /products/{id}` liefert Material- (`components`) und
Arbeitskomponenten (`labor`) mit.

## `POST`/`DELETE /api/v1/products/{productId}/components/{id}` · `.../labor/{id}`

Artikel- bzw. Arbeitszeit-Komponenten eines Produkts.

---

## `GET`/`POST /api/v1/quotes` · `GET`/`PUT /api/v1/quotes/{id}`

**Erfordert `read`/`write` auf `ResourceType::Angebote`.** Angebote.
`GET /quotes/{id}` liefert Gruppen, Positionen und die berechnete
Netto-/MwSt.-Zusammenfassung (`calculation`) — siehe ADR-0011 für die
Berechnungslogik. `PUT` mit `status: "sent"` setzt einmalig `sentAt`.

## `POST /api/v1/quotes/{quoteId}/groups`

Positionsgruppe hinzufügen (`title`).

## `POST`/`DELETE /api/v1/quotes/{quoteId}/positions/{id}`

Position hinzufügen/entfernen. **Snapshot-Prinzip:** `unitPriceNet` und
`vatRatePercent` werden vom Client mitgeschickt (z. B. vom gewählten
Artikel/Produkt/Arbeitstyp übernommen) und danach unabhängig von späteren
Preisänderungen dort gespeichert. `positionType` ist einer von
`article`/`product`/`labor`/`custom`.

**`400`** bei unbekanntem `positionType`. **`404`** bei unbekannter
`quoteId`/`groupId`.

---

## `GET`/`POST /api/v1/rates/standard` · `GET /api/v1/rates/resolve`

**Erfordert `read`/`write` auf `ResourceType::BerechtigungenSaetze`.**
Standard-Verrechnungssätze (ADR-0012). `POST` legt einen Satz an oder
aktualisiert ihn, falls (`workTypeId`, `principalType`, `principalId`)
bereits existiert (`principalType`/`principalId` weglassen = globaler
Standard). `GET /rates/resolve?userId=&workTypeId=&customerContactUid=&
workTypeDefaultRate=` löst den effektiven Satz nach der 6-stufigen
Priorität auf (Kundenvertrag User → Kundenvertrag Gruppe → Standard User →
Standard Gruppe → globaler Standard → `workTypeDefaultRate` → `0.0`).

## `GET`/`POST /api/v1/contracts` · `GET /api/v1/contracts/{id}`

**Erfordert `read`/`write` auf `ResourceType::BerechtigungenSaetze`.**
Kundenverträge (ADR-0012). `GET /contracts?customerContactUid=` listet die
Verträge eines Kunden. `GET /contracts/{id}` liefert den Vertrag inklusive
`rates`.

## `POST`/`DELETE /api/v1/contracts/{contractId}/rates/{id}`

Vertragssätze eines Kundenvertrags (gleiche `principalType`/`principalId`-
Semantik wie bei Standard-Sätzen).

---

## `GET`/`POST /api/v1/time-entries` · `PUT`/`DELETE /api/v1/time-entries/{id}`

**Erfordert `read`/`write` auf `ResourceType::StundenZeitkonto`.**
Zeiterfassung (ADR-0012). Ohne `userId`-Parameter liefert `GET` die eigenen
Einträge; ein abweichender `userId` oder `projectId`-Filter erfordert
`approve`. `POST` löst beim Anlegen automatisch den effektiven Satz über
`rates/resolve` auf und speichert ihn als `rateSnapshot` — spätere
Satzänderungen wirken sich nicht rückwirkend aus. `entryDate` im Format
`YYYY-MM-DD`.

## `GET /api/v1/time-account` · `GET`/`PUT /api/v1/work-schedule`

**Erfordert `read` (eigene Daten) bzw. `approve` (fremde Daten) auf
`ResourceType::StundenZeitkonto`.** `GET /time-account?fromDate=&toDate=
[&userId=]` liefert Wochensoll, Werktage, Soll-/Ist-Stunden und Saldo für
den Zeitraum (live berechnet, kein gespeicherter Saldo — ADR-0012).
`work-schedule` verwaltet das Wochensoll je User (Default 40h, falls keins
hinterlegt ist). `PUT` erfordert `approve`.

## `GET`/`POST /api/v1/absence-types` · `GET`/`POST /api/v1/absence-requests`

**Erfordert `read`/`write` auf `ResourceType::StundenZeitkonto`.**
Abwesenheitstypen und -anträge (ADR-0012). `GET /absence-requests?status=
requested` (für die Freigabe-Ansicht) erfordert `approve`, ebenso ein
fremder `userId`-Filter.

## `POST /api/v1/absence-requests/{id}/approve` · `.../reject` · `GET .../calendar-links`

**Erfordert `approve`.** Genehmigung legt optional einen Kalendertermin im
ersten beschreibbaren Kalender des Antragstellers an und verknüpft ihn über
`erp_calendar_links` (`resourceType='absence'`) — ein fehlender/nicht
beschreibbarer Kalender lässt die Genehmigung nicht scheitern.
`calendar-links` (Read) zeigt die verknüpften Termine eines Antrags; die
generische `calendar#links`-Route passt hier nicht, da ihr `resourceType`
eine `ResourceType`-Berechtigung adressiert und `absence` keine ist.
**`412`** wenn der Antrag nicht im Status `requested` ist.

## `GET`/`POST /api/v1/overtime-actions` · `.../approve` · `.../complete` · `.../reject`

**Erfordert `read`/`write` (eigene Aktionen) bzw. `approve` (Freigabe) auf
`ResourceType::StundenZeitkonto`.** Überstunden abbummeln (`compensate`)
oder auszahlen (`payout`), ADR-0012. Workflow: `requested` → `approved` →
`done`, oder `reject()` aus `requested`. **`412`** bei Status-Verletzung
(z. B. `complete` vor `approve`).

---

## `GET`/`POST /api/v1/invoices` · `GET /api/v1/invoices/{id}`

**Erfordert `read`/`write` auf `ResourceType::Rechnungen`.** Rechnungen
(ADR-0013). `POST /invoices` legt einen Entwurf an (`invoiceNumber` ist
`null`, bis ausgestellt wird). `GET /invoices/{id}` liefert Positionen,
die berechnete Netto-/MwSt.-Zusammenfassung (`calculation`) und
`isOverdue` (live aus `dueDate` abgeleitet).

## `POST /api/v1/invoices/from-quote`

Legt eine Rechnung an und kopiert alle Positionen eines Angebots 1:1
(`quoteId`, `title`). Keine Live-Referenz danach — spätere Änderungen am
Angebot wirken sich nicht auf die Rechnung aus.

## `POST`/`DELETE /api/v1/invoices/{invoiceId}/positions/{id}`

Positionen hinzufügen/entfernen — **nur solange `status = draft`**,
danach **`412`** (Rechnung ist unveränderlich, sobald ausgestellt).

## `POST /api/v1/invoices/{id}/issue`

Vergibt die Rechnungsnummer atomar (`R-{Jahr}-{Sequenz:05d}`), setzt
`status = issued`. **`412`** wenn bereits ausgestellt oder keine
Positionen vorhanden. Legt bei vorhandenem `project_id` ein
Rechnungsdokument (HTML) in `ERP/Projekte/<Nr>/Rechnungen` ab
(`document_file_id`) — optional, ein fehlender Ordnerzugriff lässt das
Ausstellen nicht scheitern.

## `POST /api/v1/invoices/{id}/payments`

`amount` erhöht `paidAmount`; `status` wechselt automatisch zwischen
`issued` → `partially_paid` → `paid`, je nachdem ob `paidAmount` die
Bruttosumme erreicht. **`412`** wenn die Rechnung noch nicht ausgestellt
oder bereits storniert ist.

---

## `GET`/`POST /api/v1/credit-notes` · `GET /api/v1/credit-notes/{id}`

**Erfordert `read`/`write` auf `ResourceType::Rechnungen`.** Gutschriften
(ADR-0013) — der einzige Korrekturweg für eine ausgestellte Rechnung, nie
direktes Editieren/Löschen. `GET /credit-notes?invoiceId=` listet die
Gutschriften einer Rechnung.

## `POST /api/v1/credit-notes/full-cancellation`

Vollstorno: kopiert alle Positionen der Rechnung (`invoiceId`, `reason`).
Beim `issue()` wird die Rechnung automatisch auf `status = cancelled`
gesetzt.

## `POST /api/v1/credit-notes/partial`

Teilkorrektur: leerer Entwurf (`invoiceId`, `reason`), Positionen werden
danach frei über `POST /credit-notes/{creditNoteId}/positions`
hinzugefügt. Ändert den Rechnungsstatus **nicht**.

## `POST /api/v1/credit-notes/{id}/issue`

Vergibt die Gutschriftnummer atomar (`G-{Jahr}-{Sequenz:05d}`, derselbe
Zähler-Mechanismus wie bei Rechnungen). **`412`** wenn bereits ausgestellt
oder keine Positionen vorhanden.

---

## Noch offen (spätere Phasen)

- Feingranulare Delegation der Rechteverwaltung selbst über die ERP-Ressource
  `berechtigungen-saetze` statt "nur NC-Admin" (siehe ADR-0008, "Alternativen").
- Kalendertermine ändern/löschen, Frei/Belegt-Prüfung (`checkAvailability()`),
  Termine in fremden Benutzerkalendern (Personalplanung) — siehe ADR-0009.
- Gemeinsamer Ablageort für ERP-Dateien statt pro-User-Ordner (Group Folders
  oder fester Speicherort) — siehe ADR-0009.
- Lager, Fuhrpark, betriebliche Kosten (Phase 8+).
- Echter PDF-Export, XRechnung/ZUGFeRD, Zahlungsjournal, Steuerberater-
  Export für Rechnungen (siehe ADR-0013, "Nicht Teil dieser Phase").
- API-Versionierung über `v1` hinaus, sobald Breaking Changes nötig werden.
